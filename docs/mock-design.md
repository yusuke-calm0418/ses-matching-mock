# SESモックの構成と仮仕様

既存のReact / TypeScript / ViteとGitHub・Cloudflare Pagesの構成を維持。追加依存なし。初期テンプレートの画像ファイルは削除せず残しています。

## ディレクトリ構成

- `src/components/`: 共通レイアウト、ナビゲーション、アイコン、詳細ダイアログ
- `src/pages/`: ダッシュボード、保存メール取り込み、取り込み結果確認、マッチングの実装予定案内
- `src/types/`: 案件・人材・マッチング・画面IDの型
- `src/data/`: 架空のサンプルデータ
- `src/services/`: データ取得の窓口。本格開発時はAPI通信へ置き換える想定
- `src/App.tsx`: 起動、画面切り替え、データ読み込み

## 今回の実装範囲

- 共通サイドバー、ヘッダー、デモ表示
- 登録件数と状態別件数（表示データから集計）
- 最近の案件一覧、案件名・企業名・スキル検索、ステータス絞り込み
- 案件・人材の詳細ダイアログ
- 固定のマッチング結果、適合理由・要確認条件、確認済み操作
- 5画面のハッシュナビゲーション（ブラウザの戻る・進む対応）
- 案件メール・人材メールのサンプルフォルダ確認、対象選択、本文表示、ローカル解析デモ
- 取り込み結果の編集・必須項目チェック・登録。登録内容はダッシュボードへ反映
- 確認待ち・登録済みメールの再取り込み防止（サンプルIDによる判定）
- マッチングの実行画面は未実装。既存候補の詳細はダッシュボードで確認可能

## 仮仕様・レビュー対象

- 仮のサービス名は「SES Connect」。白・ネイビーのデスクトップ中心UIを採用
- データは2026年10月29日基準の固定サンプル。実日時として表示しない
- 初期データは登録案件4件、人材3名、候補3件。追加登録に応じて案件・人材の件数と一覧が更新される。新規登録に対するマッチング候補の自動生成は未実装
- 案件は募集中・確認待ち・提案中、人材は稼働可能・確認待ち。状態遷移は今後検討
- 「取り込み確認待ち」は未登録の解析結果（案件・人材）の合計。初期値は0件。既存サンプルの登録済みデータと区別する
- 案件は取り込み日順、人材はサンプルの登録順。人材の登録日時は今後検討
- マッチングスコアと理由は固定値で、AI解析や条件計算を行わない
- 「確認済みにする」はフロントエンド内の一時状態のみ。再読み込みや画面移動で初期化
- 直リンクは `/#dashboard` などのハッシュを採用し、Pages側の追加ルーティング設定を不要にする
- 個人情報、顧客情報、APIキー、外部サービス接続、バックエンド、ブラウザ永続保存は含まない

## 次の開発順

案件メール取り込み・人材メール取り込み → 取り込み結果確認まで実装済み。次はマッチングの実行・結果表示。

取り込み方式の確定事項と本格開発への構成案は [保存メール取り込み構成](mail-import-design.md) を参照。
取り込み結果の項目、必須項目、単価の単位、ステータス、候補の比較方法を営業レビューで確認する。

## ローカル確認

`npm run dev` で起動。`npm run build` で型チェックと本番ビルド、`npm run lint` で静的検査。`npm test` で取り込み対象の絞り込み・不足項目・二重登録防止を確認（Node.js 22系を使用）。

## 文言・装飾の方針

営業担当者向けの業務画面として、次の方針を後続画面にも適用する。

- 見出しは「登録案件数」「最近のマッチング」、操作は「案件メール取り込み」など、対象と内容が分かる短い表現にする。
- 抽象的なキャッチコピー、呼びかけ、意欲を促す文言を置かない。
- 見出しやボタンと同じ内容を説明文で繰り返さない。補足は単位・集計対象・操作上の制約など、判断に必要な情報に絞る。
- 英語の飾り見出し、大きな宣伝バナー、機能を示さない図形・キラキラ装飾を使わない。
- 色は操作箇所とステータスの識別に使う。KPIや人材ごとの意味のない多色化は避ける。
- デモ環境・架空データの表示は共通ヘッダーに集約する。スコアの固定値、未実装、一時状態の制約は該当箇所に残す。
- ナビゲーションの表示名は「マッチング」とする。メール解析はローカルLLMを使う本格版の流れを固定サンプルで再現する。
- 白・ネイビーの配色、サイドバー、KPI、一覧と詳細表示の構成を維持する。
