# 保存メール取り込みの構成

## 確定した方針

営業がOutlook等からメールを手動でフォルダへ保存し、そのメールをローカルLLMで読み取る。Outlookやメールサーバーへの直接接続は行わない。案件メールと人材メールの両方が対象。

業務の流れ：**Outlook → 手動保存 → 保存フォルダ → ローカルLLM解析 → 営業による確認・修正 → 案件／人材登録**。

メールに個人情報が含まれることを前提に、実メールの処理先はPC内・社内環境を想定する。外部LLMのAPIへメールを送信する構成は採用しない。

## 本格版の構成案（未実装）

| 担当・処理 | 役割 |
| --- | --- |
| 営業担当者 | 対象メールをOutlookから保存。案件・人材の保存先を選ぶ |
| PC内または社内の保存フォルダ | 保存メールの入力元。具体的な場所は未確定 |
| 社内の読取処理 | メールファイルの形式、本文、添付情報を読み取る。重複や読取エラーを識別する |
| ローカルLLM | 読取処理から受け取った内容を案件・人材の項目に整理する。Outlookへはアクセスしない |
| 確認画面 | 元メールとの照合、必須項目の修正、営業による登録操作 |
| 本格版の保存先 | 確定した案件・人材と取込元の識別情報を保存。DBと配置は別途決定 |

保存フォルダを読むのは読取処理で、LLMに任意のファイル操作やメールアカウントへのアクセスを任せる設計ではない。実行環境と通信経路は本格版で具体化する。

Cloudflare Pages上の公開モックは架空データの操作確認用とする。本格版で社内の保存フォルダを読むには、そのフォルダへアクセスできる社内側の実行環境が必要。公開モックから社内フォルダへ接続する処理は追加していない。

ブラウザでユーザーがフォルダを選ぶ方式も選択肢だが、`showDirectoryPicker()` は対応ブラウザが限られ、ユーザー操作と安全なコンテキストが必要。単にパスを入力すればフォルダを継続監視できるという仕様にはしない。[MDN: showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)

## 保存形式と運用（仮仕様）

- メール単位で保存した `.eml` / `.msg` を候補とし、モックに両方の名前を表示する。実ファイルのパーサーは未実装。
- Microsoftの案内では、Outlookから保存するメールのファイル名は `.eml` または `.msg` になる。利用するOutlookの版・OSで保存手順を確認し、対象形式を決める。[Microsoft: Outlookのメール保存](https://support.microsoft.com/en-us/outlook/mail/save-an-outlook-message-as-a-eml-file-a-pdf-file-or-as-a-draft)
- 「営業共有 / メール保存 / 案件」「営業共有 / メール保存 / 人材」は画面上のサンプルパス。実際の共有フォルダやPC内フォルダを指定したものではない。
- モックは「フォルダを確認」を押す手動実行方式。自動監視・定期実行は未実装で、採否も未確定。
- 人材の入口をスキルシート単体のアップロードから人材メールへ変更。添付スキルシートを本格版で解析対象にするかは別途決定する。
- 本格版の重複キーはMessage-IDやファイルハッシュなどを検討する。モックの固定ID判定をそのまま本番仕様とはしない。

## モックの画面・操作

| 画面 | 操作 |
| --- | --- |
| 案件メール取り込み | サンプルフォルダ選択、メール一覧、本文・添付名の確認、対象選択、解析デモ |
| 人材メール取り込み | 同じ操作。人材メールのみ選択できる |
| 取り込み結果確認 | 元メールと固定の解析結果を表示。編集・必須項目チェック・登録 |
| ダッシュボード | 登録した案件・人材を一覧と件数に反映。未登録の解析結果を確認待ちとして集計 |

「未整理メール」には案件・人材・対象外ファイルを混在させ、種類の違いと除外動作を確認できる。種類はサンプルに設定済みの値で、実際の自動分類は行わない。

「解析（デモ）」はサンプルIDに対応する固定結果を返す。実メールの受け入れ、ファイルアップロード、本文・添付解析、AI推論、ネットワーク送信は行わない。

単価が不足する案件と稼働時期が不足する人材を用意し、確認・修正の操作を試せる。必須項目や単価の入力形式はレビュー用の仮仕様。登録済みの編集、保存の永続化、解析結果の削除・再解析は未実装。

状態はApp内で保持するため画面移動後も残るが、ブラウザの再読み込みで初期化する。既存のマッチング確認状態は従来どおり画面移動で初期化する。

## コードの分担

- `types/mailImport.ts`：保存メール、フォルダ、解析結果の型
- `data/mailFolders.ts`：架空メールとフォルダ構成
- `services/mailImportService.ts`：サンプルフォルダ取得、解析結果生成、検証、登録処理
- `pages/MailImport.tsx`：案件・人材で共用する取り込み画面
- `pages/ImportReview.tsx`：確認・編集・登録画面
- `App.tsx`：画面をまたぐ解析結果・登録データの保持
- `tests/mailImport.test.mjs`：対象選別、不足項目、修正登録、二重登録防止のテスト

本格版ではフォルダ取得と解析処理を社内の処理に置き換える。モックリポジトリにバックエンドやLLM実行環境を先行実装しない。

## レビューで決める事項

保存先（PC内／社内共有）、利用するOutlookの版とOS、メール形式、添付ファイルの解析範囲、必須項目、登録後の編集方法、再解析と重複の扱い、ローカルLLMのモデルと実行環境。
